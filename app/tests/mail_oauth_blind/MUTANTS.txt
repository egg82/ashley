(decisions.md, "A kind's secret can come from OAuth", build part 1), before the implementation existed; each has since been
applied to the built code. Each line: id, where it would live, the wrong behaviour, and the test that should go red. Equivalent or untestable
ones are listed at the end with the reason.

Equivalent or not killable here (and why)
E1   callback    take is SELECT then DELETE instead of one DELETE ... RETURNING: two truly simultaneous callbacks could both connect. Needs two
                 racing HTTP requests with a database barrier; the replay test only proves the sequential case.
E2   renewal     the exact boundary of refresh_margin_s (refresh at margin vs margin+1 s): the design does not say where the margin lives, so
                 no test pins its value; 1 s and 30 days bracket any sane margin.
E3   callback    outcome names other than the ones the Discord model gives (assumption A13).
E4   start       the pending-row cap (max_pending) for connects: the design names none.
E5   renewal     a lock around the whole renewal inside one process makes concurrent calls agree without a CAS; the tests cannot tell it from a CAS
                 within one process, only the interleaved-refresh tests (in_refresh) do, and only if the implementation takes no process lock.
